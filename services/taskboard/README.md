# Домашняя работа 01 — клиент-серверное приложение

## Условие

Реализовать понятное автору приложение с фронтендом, бэкендом, PostgreSQL и CRUD.
Применить методологию 12 факторов. Для сдачи — архив всех исходников и `Отчёт.md`:
домен, стек, сущности, аргументация по каждому фактору. Максимум 10 баллов:
5 за исходники/отчёт, 5 за соответствие 12 факторам.

## Запуск из репозитория

```sh
make up
make integration
```

Открыть http://localhost:8080. `make down` сохраняет данные в Docker volume.
Параметры локального окружения можно задать в `services/taskboard/.env` по примеру
`.env.example`. Makefile автоматически подключает этот файл, если он существует.

## Запуск из архива

Распаковать архив, перейти в его корень, выполнить:

```sh
cp .env.example .env
docker compose up -d --build --wait
```

Открыть http://localhost:8080. Если порт занят, задать `APP_PORT=18080` в `.env`.
Остановка: `docker compose down` (без `-v`, чтобы сохранить данные).

## Сдача

`make archive` создаёт `artifacts/homework-01.zip`. В корне архива находятся
`Отчёт.md`, эта инструкция, Dockerfile, Compose, Go-модуль, исходники фронтенда,
миграции, тесты и lock-файлы. Зависимости, локальные секреты и сборки исключаются.

## REST API

| Метод | Маршрут | Результат |
|---|---|---|
| GET | `/api/tasks` | 200, до 500 последних задач, пустой массив если задач нет |
| GET | `/api/tasks/{id}` | 200 или 404 |
| POST | `/api/tasks` | 201 + Location, создание |
| PUT | `/api/tasks/{id}` | 200, полная замена полей задачи; 404 если нет |
| DELETE | `/api/tasks/{id}` | 204 или 404 |
| GET | `/healthz` | 200, процесс HTTP жив |
| GET | `/readyz` | 200 если БД доступна и миграция применена; иначе 503 |

Пример тела POST/PUT (все три поля отправляет фронтенд):

```json
{"title":"Настроить мониторинг","description":"Проверить доступность сервиса","status":"todo"}
```

Название — 1–200 символов после trim, описание — до 2000, статус —
`todo`, `doing` или `done`. Дополнительные JSON-поля, NUL и некорректные ID отвергаются.
Ограничение тела — 16 КиБ; Content-Type — application/json. Ошибки валидации — 400,
неподдерживаемый Content-Type — 415, недоступность БД — 503. Неизвестный API-маршрут — 404.

## Как устроен код

- `cmd/taskboard/main.go`: конфигурация env, пул БД, запуск HTTP, shutdown и подкоманды.
- `internal/taskboard/http.go`: маршруты, JSON DTO, валидация, CRUD, таймауты и логи.
- `internal/taskboard/store.go`: модель Task, сканирование SQL-результатов, миграции.
- `internal/taskboard/migrations`: SQL, встроенный в бинарь через embed.
- `web/src/main.jsx`: один компонент React, состояние формы/списка, запросы fetch.
- `web/src/style.css`: минимальные стили.

Путь запроса: React → fetch `/api/tasks` → net/http → database/sql → PostgreSQL →
JSON → React state. Каждая запись хранится в PostgreSQL, браузер держит только
текущий список и несохранённую форму. После обновления страницы список загружается заново.

## Проверки и локальная разработка

Go 1.26.x, Node 24.x, Docker Compose:

```sh
# В корне репозитория:
make check
make integration
make migrate

# В распакованном архиве:
GOCACHE=/tmp/taskboard-go-cache go test -race ./...
TASKBOARD_URL=http://127.0.0.1:8080 go test -tags=integration ./integration -count=1
```

Для изменения React можно работать в `services/taskboard/web`: `npm ci`, затем
`npm run dev`. Vite проксирует `/api` на Go по localhost:8080. Для запуска Go
без контейнера задать DATABASE_URL на доступный PostgreSQL, выполнить
`go run ./cmd/taskboard migrate`, `npm ci && npm run build` в web и
`go run ./cmd/taskboard`. В Docker PostgreSQL не публикует порт на хост; для этого
режима нужна отдельная локальная БД или собственный Compose override с портом БД.

## Ограничения

Это локальный учебный трекер без авторизации; одна общая коллекция задач.
По умолчанию опубликован только на loopback. При публичном развёртывании нужны
TLS, доступ к приложению и внешнее управление секретами. Пагинация и конфликтное
редактирование не реализованы: список ограничен 500, при конкурентном PUT побеждает
последняя запись. Сборки фиксируют версии и lock-файлы; теги базовых образов могут
быть перевыпущены, для строгой воспроизводимости релиза нужны image digests.
