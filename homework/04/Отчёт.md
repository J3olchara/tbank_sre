# Отчёт: домашняя работа №4

## Стек и способ сбора

Приложение Taskboard: Go 1.26 (`net/http`, `database/sql`, PostgreSQL-драйвер
lib/pq), React/Vite, PostgreSQL 17.6. Экспорт метрик встроен в приложение
официальной библиотекой **prometheus/client_golang 1.25.0**. Используется отдельный
registry на процесс; Go и process collectors регистрируются явно.

Мониторинг работает в одноузловом minikube с Kubernetes 1.35.0.
**VictoriaMetrics Single v1.154.0** установлен Helm 3.19.0 из официального
чарта `vm/victoria-metrics-single` версии **0.49.0** в namespace `monitoring`,
релиз/Service `vm-single`. Хранение — PVC с запросом 1Gi, retention 1 день.
Рабочие параметры находятся в `deploy/monitoring/values.yaml`.
В архив включён полный render ресурсов Helm.

Установка следует [официальному руководству](https://docs.victoriametrics.com/guides/k8s-monitoring-via-vm-single/):
VictoriaMetrics Single имеет собственный scraper (`server.scrape.enabled: true`).
Поэтому для данной топологии отдельный vmagent не развёртывается. Статус
scraping доступен на `/targets`, запросы — на `/api/v1/query`, список имён —
на `/api/v1/label/__name__/values` того же сервера :8428.

Pull-модель: TSDB раз в **5 секунд** выполняет HTTP-запросы к каждому
обнаруженному таргету, scrape timeout — 4 секунды. Приложение не отправляет
метрики самостоятельно. Grafana в объём задания не входит.

## Экспортёры

### Рантайм Go и HTTP

`internal/taskboard/metrics.go` регистрирует GoCollector и ProcessCollector
из [клиентской библиотеки Prometheus](https://github.com/prometheus/client_golang).
Экспортируются `go_goroutines`, `go_memstats_*`, `go_gc_*`,
`process_cpu_seconds_total`, `process_resident_memory_bytes`, метрики FD и другие
стандартные метрики рантайма/процесса. Доступность Linux process-метрик проверена
на запущенном контейнере.

Дополнительно реализованы технические метрики:

- `taskboard_http_requests_total{method,route,code}` — обработанные HTTP-запросы;
- `taskboard_http_request_duration_seconds{method,route}` — histogram времени ответа.

`route` содержит шаблон маршрута (`GET /api/tasks/{id}`), а не фактический ID.
Неизвестные методы объединяются в OTHER, неизвестные маршруты — unmatched.
Имена задач, их описания и ID в метрики не передаются.

HTTP `/metrics` слушает **отдельный порт 9090**, без авторизации. На API/UI-порту
8080 такого обработчика нет (404), Service приложения публикует только 8080.
В Kubernetes metrics listener привязан к адресу pod'а и доступен внутри кластера;
9090 не опубликован наружу. Локально без env он слушает loopback; конфигурация
адреса — `METRICS_ADDR`. Временный port-forward используется для проверки.
Оба HTTP-сервера корректно завершаются по SIGTERM/SIGINT; ошибка bind любого
из них останавливает весь процесс, чтобы не оставить приложение без мониторинга.

`promhttp.HandlerFor` с EnableOpenMetrics поддерживает [OpenMetrics 1.0](https://openmetrics.io/)
через согласование Accept/Content-Type. Ответ в этом формате заканчивается
`# EOF`. Для стандартного scraper и curl без Accept также доступен совместимый
Prometheus text. Экспорт метрик не выполняет запросов к БД и остаётся доступен
при её отказе.

### PostgreSQL

В pod `postgres-0` добавлен sidecar
**quay.io/prometheuscommunity/postgres-exporter:v0.20.1**
([исходный проект](https://github.com/prometheus-community/postgres_exporter)).
Оба контейнера используют общую сеть pod'а. Экспортёр подключается к
`localhost:5432/taskboard`, публикует `/metrics` на **9187**, пароль получает
через secretKeyRef, пользователь — через ConfigMap.

Проверены `pg_up=1`, `pg_stat_database_xact_commit` и другие стандартные
метрики подключений, транзакций, блокировок и статистики PostgreSQL.
`up=1` подтверждает HTTP-доступность экспортёра, `pg_up=1` — его доступ к БД;
эти сигналы имеют разный смысл. В локальном задании используется существующий
пользователь БД приложения; отдельная роль с pg_monitor не создаётся.

## Бизнес-метрики

Все пять — **Counter**, без пользовательских labels, отдельные для каждого
процесса приложения. Начальные значения экспортируются как 0.

| Метрика | Смысл и точка изменения |
|---|---|
| `taskboard_tasks_created_total` | Число успешно созданных задач: увеличивается после успешного INSERT/RETURNING |
| `taskboard_tasks_updated_total` | Число успешных замен полей задачи через PUT: после UPDATE/RETURNING, в том числе если значения не изменились |
| `taskboard_tasks_deleted_total` | Число удалённых задач: после DELETE с RowsAffected > 0 |
| `taskboard_tasks_read_total` | Число успешных чтений конкретной задачи: после SELECT и получения записи |
| `taskboard_task_lists_viewed_total` | Число успешных просмотров списка задач, в том числе пустого: после чтения всех строк и проверки rows.Err |

Ошибки JSON/валидации, отсутствующие задачи (404) и ошибки БД не увеличивают
бизнес-счётчики. Считается успешная операция БД; последующий обрыв клиентского
соединения не отменяет уже совершённую операцию. Технический счётчик HTTP при
этом отражает и успешные, и ошибочные HTTP-ответы.

Счётчики не являются текущим количеством задач и не заменяют таблицу задач
или аудит. При рестарте процесса они обнуляются; для временных интервалов
используются rate/increase отдельно для каждой серии, затем сумма по репликам:

```promql
sum(rate(taskboard_tasks_created_total{job="taskboard"}[5m]))
sum(increase(taskboard_tasks_deleted_total{job="taskboard"}[1h]))
sum(rate(taskboard_tasks_read_total{job="taskboard"}[5m]))
```

Сумма сырых counters используется в демонстрации как проверка наличия данных,
а не как долговременное число бизнес-операций. При аварии между завершением SQL
и инкрементом возможно потерять единичное событие; transactional outbox для
телеметрии не требуется и в этой реализации не используется.

## Service discovery

В шаблоны pod'ов Deployment приложения и StatefulSet PostgreSQL добавлены:

```yaml
prometheus.io/scrape: "true"
prometheus.io/port: "9090"  # 9187 у PostgreSQL pod
prometheus.io/path: /metrics
```

VictoriaMetrics использует Kubernetes SD `role: pod`, ограниченный namespace
`taskboard-lab`. Role/RoleBinding разрешают его ServiceAccount только get/list/watch
pod'ов в этом namespace; стандартный широкий RBAC чарта отключён.
API Kubernetes используется с токеном ServiceAccount и кластерным CA.
Фиксированные IP pod'ов и статические списки реплик в конфиг не записаны.

Relabeling оставляет аннотированные Running-pod'ы и только тот declared
containerPort, который совпадает с аннотацией. Это важно: у Go есть 8080/9090,
у PostgreSQL pod — 5432/9187. Без фильтра один pod дал бы дубли таргетов.
Формируются метки job, namespace, pod и container. В результате обнаруживаются
три app-таргета (`job=taskboard`) и один exporter (`job=postgres`). Завершённый
миграционный Job в scraping не участвует.

При масштабировании приложения с 3 до 4 реплик новая цель появляется
автоматически, а после возврата к 3 исчезает без редактирования scrape-конфига.

## Проверки и демонстрация

- `make check`: gofmt, vet, race-тесты, React production build.
- Unit-тесты: OpenMetrics Content-Type/EOF и семейства метрик, 404 на публичном
  `/metrics`, отсутствие бизнес-инкремента при ошибке, ограниченные route labels,
  bind-error и shutdown обоих слушателей.
- `make integration` с API/metrics одного pod: CRUD, точные дельты всех пяти
  counters (+1), отсутствие дополнительных инкрементов от 400/404.
- `make k8s-validate`: server-side dry run Kubernetes-манифестов.
- `scripts/check_monitoring.py`: реальные запросы к API TSDB, число уникальных
  app/pod-таргетов, runtime/process-метрики, pg_up, SQL-метрики, ненулевые
  бизнес-счётчики после операций и свежесть runtime samples.
- Dynamic discovery: проверки при 3, 4 и снова 3 репликах.

В архиве есть настоящий скринкаст X11/ffmpeg: вывод Helm-релиза, pod'ов/Service/PVC
VictoriaMetrics, OpenMetrics рантайма, CRUD и ответы TSDB по up, Go, PostgreSQL
и всем бизнес-счётчикам, затем динамическое обнаружение новой реплики и `/targets`.
Команды автоматизированы, но выполняются на реальном minikube; их вывод не
подменяется и запись не ускоряется. Результаты и длительность — в `Проверка.md`.

## Ограничения

Установка локальная, одноузловая, без HA и резервного копирования. Сетевой доступ
к метрикам не публикуется наружу; дополнительная сегментация между namespace
NetworkPolicy не настраивается. TSDB и PostgreSQL используют minikube PVC;
удаление namespace/кластера может удалить данные. Рабочие пароли исключены
из архива и Git; включён только шаблон Secret. Helm values и версии зафиксированы,
базовые Docker-образы по digest не закреплены.
