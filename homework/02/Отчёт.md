# Отчёт: домашняя работа №2

## Приложение и окружение

Развёрнуто приложение Taskboard из первой работы: Go REST API, простой React UI
и PostgreSQL. React собирается в статику и отдаётся Go-процессом, поэтому отдельный
контейнер фронтенда не требуется. Используется существующий многостадийный
`services/taskboard/Dockerfile`: Node собирает UI, Go собирает бинарь,
рабочий Alpine-образ содержит только бинарь и статику, запускается от UID 10001.

Кластер — один узел minikube, профиль `tbank-sre-hw02`, Docker driver,
Docker container runtime, Kubernetes v1.35.0. Minikube v1.39.0, kubectl v1.35.0.
Приложение собрано как `tbank-sre-taskboard:hw02` внутри Docker-демона minikube
через `docker-env`; затем экспортировано `docker save` и загружено через
`minikube image load`. Это явный локальный путь без публикации образа в registry.
Образ PostgreSQL — `postgres:17.6-alpine`.

## Использованные абстракции Kubernetes

| Абстракция | Имя / файл | Назначение |
|---|---|---|
| Namespace | taskboard-lab / namespace.yaml | Изоляция учебных ресурсов |
| ConfigMap | taskboard-config / configmap.yaml | Имя БД, пользователь, порт HTTP и уровень логов |
| Secret (Opaque) | taskboard-secrets / secret.template.yaml | Пароль PostgreSQL и DATABASE_URL через env |
| StatefulSet | postgres / postgres.yaml | Одна стабильная реплика БД, pod postgres-0 |
| PVC/PV, StorageClass | data-postgres-0, standard | Постоянные данные PostgreSQL, запрос тома 1Gi |
| Headless Service | postgres / postgres.yaml | DNS-адрес БД на порту 5432 |
| Job | taskboard-migrate / migrate.yaml | Одноразовые транзакционные миграции до запуска приложения |
| Deployment/ReplicaSet | taskboard / app.yaml | Управление репликами stateless Go-приложения |
| ClusterIP Service | taskboard / app.yaml | Стабильный внутренний адрес API и UI, порт 8080 |
| Pod | Создаются контроллерами | Единица запуска контейнеров и health probes |

Default StorageClass и provisioner предоставляет minikube. В репозитории
не создаётся зависящий от хоста статический PV: том динамически выделяется по PVC.
Подход соответствует [модели StatefulSet](https://kubernetes.io/docs/concepts/workloads/controllers/statefulset/).

ConfigMap и Secret передаются через `envFrom`, реальные пароли в исходниках и
архиве отсутствуют. Скрипт создаёт случайный пароль в игнорируемом `.env` и
рендерит шаблон в stdin kubectl. Secret кодируется и хранится Kubernetes;
сам по себе Secret не означает шифрование etcd. Это локальное учебное окружение.

У контейнеров заданы requests/limits CPU и памяти; у приложения — read-only
root filesystem, запуск без root, запрет privilege escalation, сброшены
Linux capabilities и отключён автоматический mount ServiceAccount token.
PostgreSQL работает от UID/GID 70, PVC доступен через fsGroup.

### Готовность и порядок запуска

Скрипт `k8s.sh deploy` ждёт PostgreSQL, затем завершение миграционного Job,
и только после этого применяет Deployment приложения. Порядок YAML-файлов
сам по себе не гарантирует готовность; используются rollout status и wait.

Веб-процесс имеет startupProbe/livenessProbe на `/healthz`, readinessProbe
на `/readyz` с проверкой БД и версии схемы. PostgreSQL использует `pg_isready`.
Пробам и HTTP/БД заданы таймауты. Разделение readiness/liveness позволяет
убирать неготовую реплику из Service, не перезапуская HTTP-процесс только из-за
временного отказа БД. Описание механизмов: [Kubernetes probes](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/).

Повторное развёртывание пересоздаёт завершённый Job. Версии миграций и advisory
lock уже реализованы в приложении; повторный запуск не повторяет применённый SQL.
Завершённый pod Job сохраняется и имеет статус Completed — это нормальный результат.

## Взаимодействие сервисов

```text
Браузер (React)
    │ HTTP к 127.0.0.1:18080, fetch /api/tasks
    ▼
kubectl port-forward → Service taskboard:8080
    ▼
Pod Go + React (одна из реплик Deployment)
    │ PostgreSQL protocol, DATABASE_URL, DNS postgres:5432
    ▼
Headless Service postgres → Pod postgres-0
    ▼
PVC data-postgres-0 → PV (minikube storage provisioner)
```

Внутри namespace имя `postgres` разрешается кластерным DNS. Go использует
пул `database/sql` максимум на 10 соединений на реплику; три реплики могут
открыть суммарно до 30 соединений. Все задачи хранятся в общей БД, локального
постоянного состояния у веб-процессов нет. Миграционный Job подключается
к тому же Service БД и использует тот же Secret.

Service taskboard выбирает Ready-pod'ы по label `app: taskboard`; Kubernetes
обслуживает подключения к его внутреннему адресу. Для доступа с машины
пользователя использован port-forward на loopback. Port-forward к Service
выбирает один pod и сам по себе **не демонстрирует балансировку между репликами**.
Ingress и внешний LoadBalancer для этой работы не требуются.

## Масштабирование

Начальное значение Deployment — 1 реплика. Команда
`kubectl --context tbank-sre-hw02 -n taskboard-lab scale deployment/taskboard --replicas=3`
создаёт ещё два pod'а, после rollout status все три находятся в Running/Ready.
PostgreSQL остаётся в одной реплике: увеличение replicas StatefulSet без
настройки репликации PostgreSQL не создаёт работоспособный кластер БД.
Поскольку нода одна, масштабирование веб-процессов не защищает от отказа ноды.

## Ограничения

Это одноузловая локальная установка без HA, резервного копирования и TLS.
Остановка minikube сохраняет данные; удаление кластера или namespace с PVC
может их уничтожить. Пароль `.env` необходимо сохранять при повторном
использовании существующего PVC. API не имеет авторизации и публикуется
только через loopback port-forward. Образ hw02 локальный: при изменении кода
потребуются новая сборка/загрузка и перезапуск Deployment; в production нужны
неизменяемые версии образов и внешнее управление секретами.
