# Отчёт: домашняя работа №1

## Доменная область

Taskboard — небольшой трекер рабочих задач. Пользователь создаёт задачу,
просматривает список, меняет название, описание и статус, удаляет завершённые
или ненужные задачи. Приложение будет использоваться в следующих работах курса
SRE для развёртывания, балансировки, наблюдаемости и проверки отказоустойчивости.

## Стек реализации

Бэкенд: Go 1.26, стандартные `net/http`, `database/sql`, `log/slog`;
драйвер PostgreSQL `github.com/lib/pq` 1.12.3. Фронтенд: React 18.3.1,
React DOM 18.3.1, Vite 6.4.3, JavaScript и CSS. СУБД: PostgreSQL 17.6.
Docker Compose запускает БД, отдельную команду миграций и HTTP-приложение.
Go отдаёт собранный фронтенд и JSON API с одного origin по HTTP/1.1.
Node нужен только при сборке/разработке, в рабочем образе его нет.

## Основные сущности

Основная сущность — **Task** (задача): `id` (BIGINT identity), `title`
(1–200 символов), `description` (до 2000), `status` (`todo`, `doing`, `done`),
`created_at` и `updated_at` (TIMESTAMPTZ). Проверки длины/статуса существуют
как в API, так и в схеме БД. Идентификатор назначается PostgreSQL.

Служебная таблица `schema_migrations` хранит применённые версии SQL и время
применения. Это техническое состояние схемы, а не пользовательская сущность.

Все CRUD-операции доступны в интерфейсе и через REST:
POST `/api/tasks`, GET `/api/tasks` и `/api/tasks/{id}`,
PUT `/api/tasks/{id}`, DELETE `/api/tasks/{id}`. SQL параметризован,
ошибочные данные не записываются. Фронтенд выводит текст средствами React,
без вставки пользовательского HTML.

## Соответствие 12 факторам

Основа проверки — [The Twelve-Factor App](https://12factor.net/).
Ниже перечислены конкретные механизмы приложения, а также границы окружения.

### I. Codebase — единая кодовая база

Приложение находится в одном Git-репозитории, `services/taskboard` содержит
бэкенд, фронтенд и сборку. Локальное и другие окружения развёртывают тот же
исходный код/образ. Ветки короткоживущие, основной trunk — default branch
репозитория; фиксировать сдачи предполагается тегами `hwNN-vN`. ZIP — переносимый
артефакт исходников, Git-история в архив намеренно не включается.

### II. Dependencies — явные и изолированные зависимости

Go-зависимость и её версия указаны в `go.mod`, контрольные суммы — `go.sum`.
React/Vite и дерево зависимостей зафиксированы `package.json` и `package-lock.json`,
сборка использует `npm ci`. Dockerfile изолирует Node и Go на стадиях сборки.
Рабочий образ содержит статический Go-бинарь и готовую статику, без глобальных
npm/Go пакетов и зависимостей от установок на машине пользователя.

### III. Config — конфигурация в окружении

`DATABASE_URL`, `PORT`, `STATIC_DIR` и `LOG_LEVEL` читаются из env процесса.
Compose получает локальные учётные данные и порт из env; `.env.example` содержит
только демонстрационные значения. `.env` исключён из Git, образа и архива.
Для другого окружения можно передать иной DATABASE_URL без изменения исходников.
Локальный `sslmode=disable` относится к закрытой Docker-сети; внешнюю БД следует
подключать с TLS через соответствующую строку соединения.

### IV. Backing services — подключаемые внешние ресурсы

PostgreSQL — отдельный сервис; приложение использует строку подключения,
не читает файлы БД и не зависит от расположения сервера. Локальный контейнер
можно заменить внешним PostgreSQL через DATABASE_URL. Постоянный volume
принадлежит БД, а не веб-процессу. Смена ресурса не переносит данные автоматически:
при необходимости данные переносятся средствами PostgreSQL.

### V. Build, release, run — разделённые стадии

Build: Dockerfile собирает React и Go. Release: собранный образ получает
env окружения, затем отдельная подкоманда `migrate` готовит схему.
Run: тот же образ запускает HTTP-процесс без сборки, установки зависимостей
и изменения схемы. При выпуске требуется присваивать образу уникальный тег
или digest; тег `hw01` в Compose предназначен для локальной разработки,
а автоматическая публикация релизов не входит в эту работу.

### VI. Processes — процессы без постоянного локального состояния

Задачи и версии схемы хранятся только в PostgreSQL. В процессе есть пул соединений,
а в браузере — временные состояние формы и снимок списка. Сессий, локальных
файлов данных и обязательного кеша нет. Рабочий контейнер read-only.
Рестарт процесса сохраняет задачи; другая реплика с той же БД видит те же записи.

### VII. Port binding — приложение само слушает порт

`net/http` слушает `0.0.0.0:$PORT` (8080 по умолчанию) и отдаёт API и React-статику.
Внешний Apache/Node/Vite для запуска собранного приложения не требуется.
Compose публикует порт на localhost хоста. Балансировщик сможет направлять HTTP
на порт каждой реплики, без изменения бизнес-логики.

### VIII. Concurrency — масштабирование процессами

Несколько экземпляров одного образа могут работать с общим PostgreSQL:
локального состояния и sticky sessions нет. Go обрабатывает запросы конкурентно;
пул ограничен 10 соединениями на процесс. При увеличении реплик нужно учитывать
суммарный лимит подключений БД. В локальном Compose один web с фиксированным
host-port: `--scale web=N` потребует снять фиксированную публикацию портов
и поставить балансировщик. Эта топология оставлена для следующих домашних работ.

### IX. Disposability — быстрый запуск и корректная остановка

Процесс запускается из готового бинаря и не выполняет миграции при каждом старте.
SIGINT/SIGTERM запускают `http.Server.Shutdown` с 10-секундным дедлайном;
после завершения HTTP закрывается пул БД. Compose даёт 15 секунд на остановку.
Запросы к БД ограничены 5 секундами, сервер задаёт HTTP read/write/idle таймауты.
Незавершённые операции не держат процесс бесконечно. `/healthz` проверяет HTTP,
`/readyz` — доступность БД и наличие версии схемы. При отказе БД API отвечает 503,
после восстановления подключения открываются снова.

### X. Dev/prod parity — близость окружений

В разработке и тестах используется настоящий PostgreSQL, а не SQLite/in-memory
замена. Один Dockerfile собирает фронтенд и бэкенд, одни SQL-миграции и env-контракт
применимы в других окружениях. Dev-сервер Vite — только удобство редактирования:
перед сдачей проверяется собранный образ. Отдельный production-кластер пока
не развёрнут; соответствие его настроек должно проверяться при развёртывании.

### XI. Logs — поток событий

`log/slog` пишет JSON в stdout: запуск/остановку, версии миграций, метод,
путь, код HTTP и длительность запроса. Приложение не создаёт и не ротирует
лог-файлы. Сбор и хранение выполняет Docker либо инфраструктура окружения.
Строка подключения, тела запросов и SQL-параметры не логируются.

### XII. Admin processes — отдельные административные процессы

Миграции запускаются командой `/srv/taskboard migrate` из того же образа
и с тем же DATABASE_URL, что веб-процесс. Compose оформляет их как одноразовый
сервис и запускает web только после успешного завершения.
Версии хранятся в БД; PostgreSQL advisory lock защищает от одновременного
применения. Миграции выполняются транзакционно, повторный запуск не повторяет SQL.
Для новой миграции добавляется новый SQL-файл; уже применённые файлы не редактируются.

## Проверка и ограничения

Команды проверки: `make check` (формат, vet, race-тесты и React build),
`make up` (сборка/healthcheck), `make integration` (CRUD через HTTP с настоящей БД),
`make migrate` (повторное применение миграций).

Автоматические тесты проверяют Unicode и ограничения полей, ошибочный JSON/ID,
неподдерживаемый Content-Type, создание/чтение/изменение/удаление и 404 после удаления.

Учебный сервис не имеет авторизации, TLS termination, пагинации, резервного
копирования и распределённой трассировки. Список ограничен 500 записями, PUT
использует last-write-wins. Эти ограничения не требуют локального состояния
процесса и не мешают использовать приложение для следующих заданий.
Версии зависимостей зафиксированы, но теги базовых Docker-образов не закреплены
по digest; строгая воспроизводимость релизов потребует закрепления digest.
